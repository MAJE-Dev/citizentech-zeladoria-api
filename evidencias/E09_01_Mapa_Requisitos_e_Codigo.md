## Como o código funciona (explicação técnica)

- **Streams e bytes (upload).** O ASP.NET Core recebe o `multipart/form-data` como `IFormFile`. A API valida tamanho, título, executor e vínculo **antes** de ler o arquivo. Depois abre `OpenReadStream()` e copia com `await CopyToAsync()` para um `MemoryStream` de até 2 MiB, gerando o `byte[]`. Os primeiros bytes (assinatura PNG `89 50 4E 47…` ou JPEG `FF D8 FF`) precisam bater com a extensão e o `Content-Type`. O `byte[]` vai para a coluna `DADOS varbinary(max)` junto com título, nome, MIME, tamanho, SHA-256, `EQUIPERM`, `EXECUTOR` e data. O ID só é devolvido depois de `SaveChangesAsync`.
- **Bytes (recuperação).** `GET /api/imagens/{id}/conteudo` projeta apenas `Dados`/`Mime` via LINQ e devolve `File(bytes, mime)`. O ASP.NET escreve o corpo no stream da resposta de forma assíncrona. Os cabeçalhos `X-Origem-Imagem` e `X-Imagem-SHA256` deixam claro que o conteúdo vem do banco. O cliente lê com `ReadAsStreamAsync()` e copia para `FileStream` com `CopyToAsync`. O SHA-256 do arquivo recuperado bate com o do original (E05_01), o que distingue a imagem recuperada de uma prévia local.
- **JSON.** Os controllers com `[ApiController]` serializam com System.Text.Json em camelCase. Os erros saem em `ProblemDetails` (`application/problem+json`). O cliente usa `PostAsJsonAsync` e mostra o JSON formatado.
- **async/await.** Toda E/S de banco (`ToListAsync`, `SingleOrDefaultAsync`, `AnyAsync`, `SaveChangesAsync`, `ExecuteUpdateAsync`, transações) e de stream/HTTP é assíncrona e recebe `CancellationToken`, então nenhuma thread fica bloqueada esperando o SQL Server ou a rede.
- **EF Core / LINQ.** O `AppDb` mapeia as 5 tabelas com os nomes físicos do DDL. As consultas usam `AsNoTracking`, filtros opcionais (`Where`), `join` com região e categoria e contagens correlacionadas. O EF Core traduz tudo isso para um único `SELECT ... ORDER BY` (ver o log em `testes/saida/api_sessao*.log`).
- **Transação.** As duas escritas da operação "registrar atendimento" usam a **mesma conexão e a mesma transação** do DbContext. O `UPDATE` condicional (`WHERE ID=@id AND SITUACAO<>'CONCLUIDA' AND QUANTIDADEPENDENTE>=@q`) verifica e baixa o saldo numa única instrução, o que protege contra duas chamadas simultâneas. Se ele não alterar nenhuma linha, a API faz rollback e responde 409 sem gravar. A falha didática acontece **depois** do UPDATE e do INSERT terem chegado ao banco (o log mostra os dois comandos executados e o ID provisório 101), e `RollbackAsync` desfaz os dois: o estado 17,000/1 se mantém antes e depois (E07_01). Lacunas de ID depois de um rollback são normais.
- **Limitações.** Não há autenticação: `GET /api/equipe` é só identificação acadêmica. A validação de assinatura é simples e não decodifica a imagem. LocalDB é uma instância de desenvolvimento local. O indicador é proposto, não medido. Os dados de domínio são fictícios.

## Correção documentada

Veja `E09_02_Falha_Encontrada_e_Corrigida.txt`. O roteiro real encontrou uma consulta LINQ não traduzível (`OrderBy` depois da projeção por construtor), que fazia `GET /api/ocorrencias` responder 500 e mascarava o teste de 503. A ordenação foi movida para dentro da projeção e o roteiro passou de 52/54 para 54/54 depois de recriar o banco do zero.
